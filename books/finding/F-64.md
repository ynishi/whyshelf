title: "What --stale is foreseen to approve again counts approvals the frame refuses (on an upstream decided against, or on an artifact that cannot be told now), so stale can offer approving again where the run refuses"
---
What a run of judge approve --stale is foreseen to approve again (order::stale_taken), which settle reads to offer that command under an origin only when it would approve one of the approvals of the origin again (DEC-71), left out only what an upstream holds back (held_back), and its doc said a refusal of the frame is not foreseen. The frame (frame_approve) refuses an approval on an upstream decided against: denied, retired, or deprecated, with successors or without. An upstream deprecated with successors after an approval makes the approval stale (the upstream declared superseded), and holds nothing back, so the document was counted as taken, and a document standing on it too; the run refuses the first and holds back the second. When such a document is also edited, or when the link of any approved document is rewritten after the approval to a document decided against, and that document is the only degraded approval of its origin, stale offers judge approve --stale there, and the run approves nothing of it. The same holds of an approval whose Depends artifact cannot be told now, which freshness tells as a notice and not as a change, and which the frame refuses. The rule that an approval does not stand on an upstream decided against was written inline in frame_approve, and nothing said which refusals of the frame can be told before a run.

Issue #176 resolved it: the rule is one function of the ledger (Ledger::may_stand_on), the frame refusals told by the shelf and the declared statuses can be asked before a run (ApproveFrame::foresee), and what --stale is foreseen to approve again leaves out, as the run does, what the frame refuses and what stands on it (DEC-97, DEC-71).
