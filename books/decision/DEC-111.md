The adapter of rust-test answers the ask of listing (NameList) of the contract (DEC-84): a selection is one of the space file, patterns over the paths under the root read by PathGlob (DEC-63), a text that is no pattern making it no selection and its listing CannotList with why. The files it takes are chosen in the one place the space file chooses its own (Lister, beside the reading of the files of that space): the files the state of the project lists at the side, through the one tree of the run, whatever adapter of the tree the composition root chose (DEC-101, DEC-103, DEC-104), each kept where a reading would answer it as there, within the bound of bytes of a file the adapter gives, which is the bound its reading reads with; of them, those whose path ends in .rs. So it runs no program, as DEC-64 decides of a reading. Each file is read and lexed as for a name, and its items are walked into every inline module: each function that carries a test attribute is a test, told in one place for finding, the items beside (DEC-90) and listing, and is named by its file, its modules and the function, each segment as the source spells it, the name read back by the one reader of the grammar or counted as one that cannot be written. Twins are one name, the first in the order of the file. A listing is all of them only when nothing kept it from being so; it is some of them, with why, when what would keep the space file's listing from being whole is so, when a file taken cannot be read, is not UTF-8, does not lex or nests too deep, when something in a file may make a test the scan does not see, when a name cannot be written, past the bound of names, which is of the tests and counted where their names are made, and past the files or the bytes in all one listing reads, where it stops, the size of a file looked at before it is opened so that no file is read past the bound; the reason names the first few files, each with the first thing found, and counts the rest, and is written, with the space file's, in one place. What may make a test is: an item macro call; an inner attribute that is not inert; an attribute that is not inert on any item (an impl, a struct, an enum, a trait, a const or a static as much as a module or a function), since an attribute macro there may write test functions; on a test, an attribute beside its test attribute, which may write more tests, while the test named still resolves as it does; a test attribute that is a path (tokio::test), a macro of a crate that may write more than one test, the function still listed as the test of its name; a module out of line read by #[path] from a file that does not end in .rs, or by a path the scan cannot read as one literal, which no listing takes; and a derive other than those of the standard library (INERT_DERIVES), which are inert under std or core, or by a bare name only when, in the module the derive is written in, no use names an item so (as the last segment of a path or an alias) and no glob use is written, since a use may bring a crate's derive in under that name; the scope is the module's own, as Rust resolves a name, so a use of a module around it or in it does not reach it. An attribute is inert when the language defines it as a built-in attribute that is no macro (the Reference's index of built-in attributes, INERT_ATTRIBUTES), or is of a tool; test and derive are read on their own, and an attribute of a crate, a derive's helper among them (serde, error, command), is none, since whether what a crate's macro writes holds a test cannot be told without expanding it.
