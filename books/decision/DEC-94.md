rekey <ref> changes one document per run. It gives it the key new would take (DEC-28), or the --key given when that is free, and moves its file where new would put it, <book dir>/<key>.md; the identity stays, and its key: and the items of the links that mean it are rewritten, no body and no other field, so no hash changes. The document is one file whose identity and key read, valid or not, since both files of a key written twice are invalid (DEC-36). Who writes a key has one owner, KeyWriters, made once by the build and read by new, check, a link and a reference alike: every file whose key: reads in the grammar of its book, valid or not, whatever its id:. The same owner says whether that set is whole, as a file of the book of the key that could not be read at all may write the key; the documents that write the key in a link are read from every file, invalid ones too, with the places that could not be read. rekey goes on only when both are whole: a file that could not be read and may write the key or link to it, or a link entry that is no list, is listed and stops it. A link writes a key as text, so after a merge nothing in a file says which document it meant. For each document that writes the old key in a link, the meaning is decided by evidence: when the document renumbered is the only writer of the old key, the link follows it; else the approval that stands about the document of the link, when it is an approval, pinned for that link the document renumbered, another writer, or both; else the caller says --follow, --stay or --both. A word that agrees with the evidence, or --both, decides; a word against it, or pins on both sides with no --both, is a contradiction. Nothing is decided by a default: every document undecided or contradicted is listed and nothing is written, as a default for a link that is not known takes the link of the other branch. The answer names --both where a document may have meant both. The files are written in the form fmt writes, by the rule of fmt for a file it would leave alone; before anything is written they are read back as the adapter says, built as the books are built and held against the plan (the document in one file with the new key, each link where its meaning puts it, no file with a problem it did not have), and every difference is listed. Then they are written all or none: the new file made, the others written over, those put on disk, the old file removed and that put on disk; a stop before the removal is undone in reverse, and when that cannot be done the files not put back are listed. The ledger is never written: an approval pinned the identity it stood on, and the identity stays, so whether each approval holds is computed from the files after the write and told in the answer. The body of a document that names the old key is not changed, and is listed. Two branches that each ran new for one key conflict on one file, as new names a file after its key: a person separates the sides first, the side of the main branch back in that file and the side of the branch in a file of its own, and a file with conflict markers left in it reads no front matter and stops rekey as above.
