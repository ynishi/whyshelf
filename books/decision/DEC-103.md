title: "The tree of the project in a commit of Git or in its index is read by GitStates, from one listing of each side, its files converted by the attributes of that side"
---
GitStates reads the tree of the project at two sides: a commit before a change, and a commit or the index after it. Each side is listed once in a run, when first asked (ls-tree -r -t -z --full-tree of the commit, or ls-files -s -z of the index, its directories made from the paths), within a bound of bytes (LIST_BOUND, changed for a test of the bound); past it, every name of that side cannot be told. A name is looked up part by part in the listing: a link is told with the text it holds and where it leads, the text resolved in the tree from the directory of the link (an absolute text, and one that goes above the top, lead out of the tree; a link on the way is resolved again, up to the walk's bound of links, past which and through a file or a submodule on the way it is unresolved; nothing there is broken; the top itself is the top); a submodule, and a path the index holds a conflict at, cannot be told; a directory has no bytes; a file is its content converted as a checkout writes it, by the attributes of its side (git --attr-source of the commit; for the index, HEAD's, read only while the index's .gitattributes are HEAD's, blob for blob), every filter driver the settings define shut out, at most one byte past the bound held, each file by its own cat-file --filters (a batch writes the size as stored before the converted content, so it cannot be read apart), the texts of the links by one cat-file --batch -Z fed only object names a listing gave. A look reads the content of a file and counts its bytes, holding none: a pipe the reading of a directory waits on is no part of a commit, so the reason a look of the file system opens nothing does not hold here, and the cost is the bytes of the files looked at. The entries of a directory are those of the listing, each with its kind (a tree a directory, a blob a file, a link a link, a submodule another kind), and the files of the tree are every blob, link and submodule. Neither side reads what the system resolves (a link out of the tree, a place that is no name of it, built docs outside), with the one reason LEAVES; both sides are read; no address is named. A side is written in what a reader says as <rev>:<path>, or :<path> for the index. Opening the tree asks that the root is in a repository, that each revision names a commit (one that starts with - is none, so it cannot pass an option), and that this Git knows every form the reading uses, each tried once, by the one list of them (TreeCall) the reading runs: a usage it does not know names the form, and the tree is not opened. It also asks, for the index, that its .gitattributes are HEAD's. Nothing is written: no object, no index, no ref. What it reads may differ from a directory of the same project: an untracked file is not there, a submodule cannot be told, a file a filter driver names is read as a checkout that runs no driver writes it, and a link that holds an absolute path leads out of the tree wherever it points. It may differ from a checkout of the same commit too: only the attributes the side holds and the repository's own (info/attributes) convert a file, never those of a person's settings (core.attributesFile, and the file Git reads by default) or of the system, which no call of Git reads, so nothing outside the repository chooses how a file is converted; and a path the index holds by intent to add (git add -N) reads at the index side as an empty file, since ls-files -s writes it as one and nothing the reading asks tells the two apart. The cost: each converted file is one process of Git, so a reading of many files (the listing of a selection's names among them) starts one for each file it reads or looks at.
