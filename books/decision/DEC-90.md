The text a name of the space rust-test comes to is the test's own text (DEC-64), twins joined in the order of the file, then the text of every other item of the test part of its file, in the order of the file. The test part is the outermost inline module on the way to the test that carries a cfg holding only under test, as an outer or an inner attribute (test, an all of which one holds only under test, or an any of which each does), or the file when none on the way does; twins of a module on the way may be two parts, and each is taken once, in the order of the file. Every item of the test part is taken, the items of the inline modules in it included, except every function rust-test reads as a test, wherever it stands. A module in the part is read through, not taken whole: its name, its visibility and its braces are in no line; each line of an item inside it starts with a mark without a name of how many modules of the part it is in, as many > (no item starts with >, so a mark is never taken for an item, and a line of the part's own level has none), then the attributes of those modules, outer then inner, outermost first, so that they stay tied to the items they apply to; a module with no item but tests is no line, and an item moved into or out of a module, two items of one name swapped across its boundary among them, changes the text. So it keeps REQ-33 and DEC-80: a module renamed inside a test part, made public, or of tests only added to it, changes no text beside, and a move by prefix (judge moved --prefix) follows the test while the other tests of the part stay fresh. Known limitation: where two sibling modules at one depth, with the same attributes, meet, the boundary can shift over their items in their order and change no line, so which module an item is in, and what a test calls by a path or a glob use, can change while an approval of the test stays fresh; this is accepted only there, for items at one depth, in one order, across sibling modules. So an edit of a helper, a use, a constant, a type, an impl or an item macro call there makes every test of the part read as changed; an edit of another test, or of the code under test outside the test part, changes nothing. A function made a test by an attribute rust-test does not read as one (rstest, test_case) and a test written inside an item macro call (proptest) are items beside, so an edit of one makes the other tests of the part stale: the error is toward stale. What a test reaches outside its part is held too, after the items beside it, so that a helper kept in another file, or in a module of the crate under a cfg of test, makes stale the tests that use it and no other. The modules of a crate are read from the root file of each target the manifests of the project name (library, binaries, integration tests, benches, examples), a module declared out of line being found by the rules of the language (x.rs or x/mod.rs, a path attribute, the directory of the stem of a file that is neither a root nor a mod.rs). An item is compiled only under test when a cfg that holds only under test is on it, on a module around it, or inside the module's file as an inner attribute, or when it is of an integration test; any other item is compiled always. A test holds a module compiled only under test when a path in its text (its own, the items beside it, the held text of a module or item it already holds, each once) names it: a path is two or more identifiers joined by ::, or a leaf of a use tree, resolved from the module it is written in (crate, super and self as the language has them); a segment that no module resolves (a name a use brought in, an alias of a module of code, a glob, the body of a macro defined by macro_rules!, a lone identifier in the arguments of a macro that is not of the standard library or a logging one) holds the module of that name, toward stale; a local, a parameter or a field named like a module holds nothing. A test-only item outside every test-only module (a function, a constant or an impl in a module of code) is held by its name, and an inherent impl or a trait by the name of one of its associated items after . or ::. What a held module or item names is held in turn. What no name reaches is held by every test of its crate: a module that defines an exported macro or stands under macro_use, one that holds an impl of a type it does not declare, a trait impl or a derive under cfg_attr(test), an impl with no associated item and an item macro call, all under a cfg of test. The code compiled always, the code under test, is never held, so an edit of it still leaves its inline tests fresh. A file an include reads by a literal path is held as the SHA-256 of its bytes, so a fixture that is read by include_str! is held; one read as the test runs (std::fs::read) is not. Where what a test would reach cannot be read (a module declared out of line whose file is not there or whose path attribute is not one literal, an include whose path is no literal, a file of no target while something of the project could not be read, a crate past the bounds of its files and bytes), the test cannot be told, and only a test that would reach it: its approval stays as it is, with a notice, not toward stale. What a test holds is printed as the items beside are, in the order of the file and of the module, each module or group of items after a line @ <file> <module> (no item starts with @), each include after a line @@ <path> <hash>. A test lives in its own file and in the files it holds (DEC-99). Each item is printed as a test is, doc attributes left out, and the test and the items beside it are joined in one fixed form that does not mistake one for the other: each item on a line of its own after the test's text, two parts apart by an empty line, and none of them a test. Nothing in a body is parsed: the items are taken as tokens, the paths that name a module are the only thing read in them, and no call is followed to the item it reaches. The bounds of bytes and of depth, and the answers of cannot tell, stay as they are. The names, the preset test and the asks stay as they are; an approval of a test made before reads as stale once, unless nothing is beside the test and it holds nothing, whose text is then its own as before. Of DEC-64, this replaces the sentence that the text is the function alone, so that what it calls is not compared, and its saying that present gives the function's own tokens; it keeps DEC-64's names, its scan of items that runs no program, its bounds, its answers and its preset test. Of DEC-56, this adds to its body that a helper used by one feature, kept in its file, is held by the text of each test of the file a verification names by function, and rewrites its first rejected reason, that no space named a test function, into why one file for every feature would still make every verification stale; it keeps the rest of DEC-56: a file of end-to-end tests per feature, the guard on how many verifications name one file, and the names of the temporary directories. The shared helpers of those files, common/mod.rs, are held by the text of the tests that reach them and named by no verification (DEC-56).
